# Code and config

- Comments say the reason in words. They never cite a decision by number alone ("Q38"), which a later reader can't look up; name the document if a source is needed.
- Config files stay close to tool defaults; each deviation gets a one-line comment saying why.
- Zod schemas are PascalCase with a `Z` prefix, types and interfaces with a `T` prefix, most general word first: `ZCardQA` and `TCardQA`, `ZDeck` and `TDeck`. No lint rule enforces it (oxlint has none); review does.
- File names: React components are `PascalCase.tsx` (`Session.tsx`); other modules are lowercase with a dot suffix for their purpose (`session.helper.ts`, `card.schemas.ts`, `review.storage.ts`). A test file adds `.test` before the extension (`session.helper.test.ts`) and sits next to the code it tests.
- Start a new test file for each feature; a test file stays under 400 lines. It is named after the component the feature lives in (`CardView.test.tsx`), or after the feature when it runs through the whole App (`Navigation.test.tsx`, `German.test.tsx`). A feature too big for one file is split by sub-feature, named after it (`CardEditor.edit.test.tsx`). Helpers that two or more test files use go in `apps/web/src/test/`, each file with a one-line comment that says what its exports do and changes when an export moves in or out. A test moved to another file keeps its seam: one that renders `App` keeps rendering `App`.
- Follow the patterns of the code nearby before you introduce a new one; when you introduce one, say why in the pull request.
- Styles use only the design tokens (`apps/web/src/tokens.css`, a copy of `docs/design/tokens.css`); `styles.test.ts` checks it. Allowed raw values, none of them a colour or a size: `0`, `100%`, `100vh`, `-1` in `calc`, the commented breakpoint, integer `z-index`, `color-mix` percentages, `fr` fractions, and the count in `repeat()`, as in `repeat(2, 1fr)`; the count passes whatever the track, and the track is checked on its own. A prototype rule with any other raw value is left out with a comment. Custom properties must be tokens from `tokens.css`: a component-local one, like the prototype's `--progress`, fails the check, so set such a value inline in the component.
- A `@media` rule comes after the base rule with the same selector; otherwise the base rule wins. `styles.test.ts` checks it.
- Use native elements (`button`, `a`, `input`) for anything interactive; add ARIA roles only where no native element fits. Never nest interactive controls, not even with `role="button"` (ARIA treats its children as plain content): place them side by side and let CSS make one fill the row.
- A field for a one-line value (a number, unit, ID, tags, lesson) is an `<input>`; a `<textarea>` is for prose that may run to several lines.
- An icon-only button hides its icon (`aria-hidden="true"`) and has the same text as `aria-label` and `title`.
- A group of repeated rows (a Card's options) is a `<fieldset>` with a `<legend>` and one hint, linked by `aria-describedby`; each row's errors are keyed `<language>.<field>.<index>`.
- A control that can be disabled has a disabled style.
